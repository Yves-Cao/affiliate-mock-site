# 评审到研发门禁图绘制说明

版本：v0.1  
状态：文字资料已整理；待绘制与项目负责人确认执行安排。  
用途：让管理层、产品、设计、研发、CRM团队、测试、运营、财务和审计判断项目是否具备研发启动条件。

对应[Mermaid流程图预览](20-评审到研发门禁图-Mermaid预览.md)已生成，包含研发启动及冻结后变更两图；门禁和箭头均为条件关系，不代表实际签核或启动已发生。

## 1. 范围与需要回答的问题

起点是评审材料准备，终点是明确范围的研发启动结论。立项方向已有确认，图中作为前置背景引用，不要求重新审批商业机会。

主线展示需求评审、设计评审、技术评审、测试评审、版本冻结和研发启动。会议可以合并，四类结论必须独立留存。资料编制和问题修订可以并行，不能把召开会议等同于门禁通过。

本图是流程要求，不表示当前四类评审已经完成。实际状态取自签核记录、阻塞日志和[当前工作台](../当前工作台.md)。

## 2. 责任泳道

| 泳道 | 图中责任 | 应交出的记录 |
| --- | --- | --- |
| 产品与项目负责人 | 维护范围、版本包、问题分流、评审安排和启动范围 | 资料索引、议程、待办、决议及启动记录 |
| 业务、运营与管理层 | 确认目标、价值、业务规则、优先级和责任资源 | 需求决议及授权范围 |
| 设计、产品与原型实现 | 核对页面任务、交互、异常、权限和Mock同版 | 设计决议、问题修复与走查证据 |
| 前端、后端、CRM及相关系统 | 核对事实源、读写边界、模型、API、事件和非功能方案 | 技术决议、契约、联调计划与依赖证据 |
| 风控、财务与审计 | 核对风险/资金边界、审批、账务、参数与留痕 | 专业意见、参数责任和批准记录 |
| 测试与验收负责人 | 确认测试范围、场景、数据、验收和发布阻断 | 测试决议与验收基线 |

真实姓名、授权代表和排期由项目管理记录补齐；不在图中虚构负责人已到位。

## 3. 节点与阶段产物

| 节点 | 内容 | 进入条件 | 输出或退出条件 |
| --- | --- | --- | --- |
| G01 | 组装同版资料包 | 本轮MVP范围和现行入口已确定 | 项目介绍、PRD、规则、页面、技术、测试及问题清单可访问 |
| G02 | 会前完整性检查 | G01资料可读取 | 缺口有对象、责任角色和影响说明；未齐备部分不伪装完成 |
| G03 | 需求评审 | 商业背景、范围、规则、竞品结论、指标与验收可讨论 | 明确采纳/修改/不采纳、范围及关键业务待决 |
| G04 | 设计评审 | 需求边界明确；页面和演示场景对应同版需求 | 正常与异常路径、状态、权限、响应式和页面问题形成独立决议 |
| G05 | 技术评审 | 领域边界、数据事实源、接口与外部依赖资料可核对 | 模型、API、事件、幂等、补偿、安全与性能方案有结论 |
| G06 | 测试评审 | 需求及契约达到可测试程度 | 测试范围、用例矩阵、验收、证据及发布阻断条件冻结 |
| G07 | 问题闭环核验 | 四类评审问题已记录 | 阻断项关闭有证据；允许带入项有批准和明确边界 |
| G08 | 契约与API Mock校验 | 主规则和契约问题已解决 | API/事件Schema、错误码、权限及Mock同源与场景检查具备证据 |
| G09 | 冻结研发基线 | G07/G08及相关专业门禁满足 | PRD、页面、OpenAPI、事件、Mock和测试版本清单唯一且可追溯 |
| G10 | 建立开发跟踪 | 冻结范围可分解 | 一份D级实施追踪矩阵、变更日志和阻塞依赖日志建立 |
| G11 | 研发启动判断 | 资源、环境、范围、责任和前置门禁已核对 | 授权人给出Go、Conditional Go或No-Go |
| G12 | 开始获准范围研发 | G11允许启动且团队取得同版资料 | 开发任务引用基线，后续改变进入变更管理 |

G05技术资料可在G03之前准备；G08的API Mock也可提前制作。图上应区分“提前编制”与“门禁验收”，不把全部产出排到最后才开始。

| G02 | G03 | 资料足以开展有效需求评审 |

| G03 | G04 | 评审范围及主链规则已明确，残余项不使设计失去依据 |
| G04 | G05 | 页面责任、状态和关键异常可映射技术对象 |
| G05 | G06 | 接口/数据/权限设计可形成可执行验收 |
| G03/G04/G05/G06 | 对应资料责任人 | 驳回或需修改时，登记问题并按影响修订 |
| 修订结果 | 原评审节点及受影响下游 | 新规则影响多个专业时，复审受影响部分 |
| G06 | G07 | 四类独立结论、待办和签核记录齐备 |
| G07 | G08 | 关键业务、资金、安全、权限和主链阻断具备关闭证据 |
| G08 | G09 | 契约、Mock及必要检查通过，版本不存在未处理分叉 |
| G08 | G05/G06 | Schema或场景失败、不可测试或不可兼容，退回相应专业处理 |
| G09 | G10 | 发布本轮冻结清单和变更入口 |
| G10 | G11 | 实施、变更、阻塞三份跟踪材料及责任齐备 |
| G11 | G12 | Go；或Conditional Go明确授权的范围 |
| G11 | 对应阻断责任人 | No-Go；补齐证据后重新判断 |

## 5. 各类评审的最小资料

| 评审 | 必须预读 | 必须留下的判断 |
| --- | --- | --- |
| 需求 | 项目介绍、PRD、规则/状态/参数、需求矩阵、Cellexpert报告与影响处理、待决项 | MVP/非范围、规则及例外、验收是否成立 |
| 设计 | 页面契约、设计规范、同版Mock、演示脚本、权限与状态、已有走查证据 | 页面与业务一致、关键流程可操作、异常和拒绝路径完整 |
| 技术 | 系统边界、逻辑架构、数据模型、CRM事实清单、API、事件、安全、联调与补偿 | 事实源/读写边界、执行一致性、资金幂等和外部能力可落地 |
| 测试 | 测试方案、全量用例矩阵、数据底座、场景、UAT与证据要求 | 正反例、并发和异常可测；发布阻断条件明确 |

开发前不要求全部自动化测试代码编写完成，但范围、用例矩阵、验收标准和发布阻断条件必须先冻结。Cellexpert后台实测保留为补充核验，不作为新增的冻结阻塞项。

## 6. 阻断、带入与启动结论

| 情况 | 图上的路径 |
| --- | --- |
| 核心资金规则冲突、事实源不明、敏感权限未定、主链无法验收 | 阻断，回到对应评审；不能用占位数据放行 |
| 真实CRM连接、认证、归因事实或打款能力缺必要证据 | 按受影响范围登记技术依赖；主链启动是否可放行由授权评审决定，不代签 |
| 非关键文案、局部视觉细节、补充竞品实测 | 经对应评审批准可带入，必须有责任、期限、关闭证据和逾期影响 |
| 生产参数尚无签核 | 配置结构可评审；不把Mock数值转成生产值，不放行依赖该参数的生产执行 |
| Go | 本轮获准范围全部前置条件满足 |
| Conditional Go | 写清获准/禁止范围、带入项、责任和阻断条件；不能无条件启动整个系统 |
| No-Go | 前置问题影响安全、资金或主链，暂停相关启动，保留可继续的资料工作 |

## 7. 变更与审计连接

冻结后变更从“变更申请”进入“影响评估”，关联受影响的规则、页面、API、事件、Mock、测试和迁移，再经相应评审形成新基线。普通实现待办不能暗中改变已确认业务规则。

每次评审或启动决定至少关联资料版本、议题、结论、适用范围、批准人及授权、时间、待办与关闭证据。全部生产变更按D级管理；紧急止血允许先执行，24小时内补记录，该例外不能用来绕过常规研发启动审查。

## 8. 绘图验收

- 可以看出四类评审各自输入和输出，失败后返回正确责任环节。
- 能区分材料已准备、Mock局部通过、专业评审通过、研发启动和生产验收。
- API Mock、契约和测试冻结在启动前有明确检查节点。
- Conditional Go具有范围和截止条件，不能被画成默认Go。
- 现有阻断、真实签核人与未确认参数没有被图形自动核销。
