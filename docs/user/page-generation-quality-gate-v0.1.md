# 用户端页面生成质量门禁

版本：v0.1
日期：2026-11-11
状态：Active

## 目的

这份门禁用于避免用户端 Mock 页面只满足功能，却出现信息层级混乱、间距失衡、组件拼凑和移动端拥挤的问题。页面只有同时通过结构、视觉和交互检查，才可标记为完成。

## 页面生成顺序

### 1. 证据和范围

生成前必须读取：

- `DESIGN.md`
- 用户端页面设计规范
- 当前页面对应的单页规范
- 当前 Mock 的路由、组件和数据结构
- 用户本轮已确认的交互要求

当前会话只修改用户端 Mock，不修改管理端、生产规则、CRM、支付或真实接口。

### 2. 页面契约

写代码前先明确：

- 页面目标和主要任务
- 页面入口、退出和返回路径
- 信息优先级：首屏主信息、辅助信息、渐进披露信息
- 区域布局、宽高关系和主要对齐线
- 字段、控件、默认值和可操作状态
- Loading、Empty、Error、Disabled、Forbidden、Success 状态
- 桌面端、平板端和移动端变化
- 关闭、返回、Escape、遮罩、焦点和滚动行为
- 数据来源、Mock 状态变化和刷新后的持久化行为

没有页面契约时，不直接进入视觉和代码实现。

### 3. 视觉构图

页面必须先形成布局草图或结构说明，再实现组件：

- 确定页面唯一主视觉和主要操作
- 先安排页面级区域，再放卡片和字段
- 卡片、表格、抽屉和操作栏必须使用已存在的组合模式
- 间距优先使用4px、8px、12px、16px、24px节奏
- 同一页面的边界、圆角、标题层级、按钮高度和状态色保持一致
- 不为了填空增加装饰卡片、重复标题或无业务价值的说明
- 页面必须有明确的内容密度，不能只有大面积留白，也不能把所有内容堆在首屏

### 4. 实现约束

- 优先复用现有抽屉、表格、步骤条、筛选器、按钮和状态组件。
- 新增样式必须能说明对应的页面需求，不用临时值覆盖全局设计。
- 不把 Mock 数据、演示金额、天数或状态写成生产规则。
- 不增加用户未要求的流程、审批、打款或真实接口行为。
- 状态变化必须有唯一来源，不能由多个页面各自维护相同状态。

## 视觉验收

### 结构检查

- 首屏能看出页面用途和下一步操作。
- 标题、说明、数据和操作的层级明确。
- 相关内容并排，不相关内容分组。
- 页面不出现卡片套卡片、重复标题或空白占位区域。
- 抽屉和弹窗的宽度、内容滚动区、底部操作区稳定。

### 截图检查

至少检查以下视口：

- 1440 × 900
- 1024 × 900
- 390 × 844

每个视口检查：

- 主体是否横向溢出
- 文本是否被裁切或挤压
- 组件是否保持固定尺寸
- 视觉重点是否仍然清楚
- 间距和对齐是否稳定
- 抽屉、弹窗和底部操作是否遮挡内容

### 交互检查

- 入口、返回、关闭和取消都有明确结果。
- 进入、退出和刷新后状态保持一致。
- 未完成、已完成、锁定和错误状态都能被解释。
- 键盘 `Escape`、遮罩点击和焦点回收符合全局规范。
- 移动端不依赖悬浮才能完成关键操作。
- 任何可点击控件都不会出现“点击无反应”。

## 反向审查

完成后必须主动问：

1. 是否只是把需求逐项塞进页面，缺少主次？
2. 是否有新造但没有设计依据的颜色、圆角、阴影或间距？
3. 是否存在同类页面使用不同的抽屉、按钮或状态词？
4. 是否有内容在桌面端好看、移动端却被压缩？
5. 是否有未来数据、错误状态或 Mock 状态提前影响页面？
6. 是否能用一张截图解释页面结构，而不需要额外口头补充？

## 完成证据

完成页面必须同时记录：

- 修改文件
- 页面契约或变更说明
- 自动化测试结果
- 至少一张桌面截图和一张移动端截图
- 已知残留问题及冻结原因

功能测试通过但截图检查未通过时，页面仍视为未完成。

## 本门禁的冻结规则

已通过并记录的页面质量问题不重复打开。后续只有在用户明确改变需求、设计规范或页面范围时，才重新评估冻结结论。
